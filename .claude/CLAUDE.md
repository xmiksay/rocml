# rocml — Project Brief

Standalone Rust LLM inference engine for Qwen3.5-hybrid/Ornith and dense Qwen3, with hand-written HIP kernels tuned for AMD gfx1101 (RX 7800 XT). GGUF weight loading, OpenAI-compatible server. No candle, no rocBLAS/hipBLASLt, no bindgen — kernels and the HIP runtime binding are hand-written and hand-tuned in this repo.

This brief wins over `../CLAUDE.md` for anything specific to this project.

## Crate map

- `rocml-hip` — minimal safe wrapper over the HIP runtime C API (hand-written FFI, no bindgen), linked against `amdhip64`. Device/stream/buffer/module/kernel-launch primitives only — no ML logic here.
- `rocml-kernels` — HIP C++ kernel sources under `kernels/`, compiled to code objects (`.hsaco`) by `hipcc` in `build.rs` and embedded into the binary via `include_bytes!`. Exposes kernel bytes + entry point names for `rocml-hip` to load and launch.
- `rocml-core` — hardware-agnostic CPU-side building blocks: mmap'd GGUF v2/v3 parsing, ggml quant (Q2_K..Q6_K, Q8_0) CPU dequantize, and a byte-level BPE tokenizer built from GGUF `tokenizer.ggml.*` metadata (pre-tokenizer regex selected per `tokenizer.ggml.pre` — qwen35 vs qwen2 families).
- `rocml` — the engine: GGUF config/weight loading onto the GPU, a per-layer-per-kv-head-plane KV cache, the single-token decode-style forward pass, sampling (`src/sample.rs`), and generation (`src/generate/`). `src/model.rs` dispatches on `general.architecture`: `"qwen3"` runs the dense forward pass (`src/forward/`); `"qwen35"` runs the hybrid Gated Delta Net + full-attention forward pass (`src/qwen35/`) — every `qwen35.full_attention_interval`-th layer is full (softmax) attention, the rest are linear-attention GDN layers with persistent per-layer conv/recurrence state (`src/qwen35/cache/`). `src/snapshot/` is the conversation-state checkpoint/restore layer (issue #1, qwen35-hybrid-only) — see "Conversation-state snapshots" below.
  - Both architectures' decode-step full-attention layer (the dense model's every layer; qwen35's full-attention layers) shares one fused kernel, `Kernels::attn_decode` (`src/forward/kernels.rs`, wrapping `rocml-kernels`' `kernels/attn_decode.hip`): flash-decoding-style online-softmax causal attention, split-K over the sequence axis for occupancy at depth, one workgroup per (kv head, split) covering that kv head's whole GQA q-head group so K/V loads are staged into LDS once and shared — two kernel launches total (`attn_decode_partial_f32` + `attn_decode_reduce_f32`) per layer per decode step, replacing a former per-q-head `gemv_f32`(scores)+`softmax_varlen`+`gemv_t_f32`(weighted-V) composition (~2*n_heads+1 launches/layer). See the `.hip` file's module doc for the occupancy math and the GQA/quantized-KV design notes.
  - GDN supports grouped key/value heads (`qwen35.ssm.group_count` < `qwen35.ssm.time_step_rank`, e.g. Ornith-1.0-9B's 16 key / 32 value heads): `gdn_recurrence_decode_f32` broadcasts key head `h % num_k_heads` to value head `h` — a **tiled** pattern, not the naive `repeat_interleave` HF transformers' source uses on the raw checkpoint. llama.cpp's GGUF converter already permutes every value-head-indexed GDN tensor (V, Z/gate, beta, alpha, A_log, dt_bias, conv1d's V channels, `ssm_out`'s input columns) from HF's grouped order into this tiled order at conversion time (`_LinearAttentionVReorderBase._reorder_v_heads` in `convert_hf_to_gguf`'s `conversion/qwen.py`), specifically so a cheap modulo broadcast works at inference — using `/` instead of `%` here loads and runs without error but produces well-formed, deterministic, finite garbage (verified against Ornith: fixed a real regression this way — see the kernel's own doc comment for the full citation). When `num_k_heads == num_v_heads` both formulas coincide, which is why this was invisible on Qwen3.5-2B.
  - Linear-layer weights are loaded through `weights::LinearWeight` (`src/weights/linear.rs`), shared by both architectures: a tensor whose dtype is Q8_0/Q4_K/Q5_K/Q6_K and whose row length is a multiple of that fused kernel's block width (32/256/256/256) stays in its raw GGUF block format in VRAM and runs through `Kernels::gemv_quant` (dispatching to `rocml-kernels`' `gemv_q8_0`/`gemv_q4_k`/`gemv_q5_k`/`gemv_q6_k`); everything else (F32/F16/BF16, an unsupported quant, or a non-conforming row length) falls back to the original CPU-dequant-to-f32-then-f16-upload path. This is what lets a Q6_K model like Ornith-1.0-9B (~7.5GB) fit in 16GB VRAM at all — dequant-to-f16 would not. The token embedding table stays f16-dequantized always (the embedding-lookup kernel only reads f16); the output/lm-head projection goes through `LinearWeight` like every other linear layer.
    - **Decode bandwidth (issue #7)**: every `gemv_q*.hip` kernel now owns `ROWS_PER_WG` (2, `kernels_quant::GEMV_ROWS_PER_WG`) consecutive output rows per workgroup instead of one — at the smallest served `m` (4096: qkv/attn-out), one row per workgroup meant a workgroup's whole lifetime was a single iteration of uncovered memory latency; 2 independent per-lane weight loads per iteration gives the scheduler something to overlap that latency with (measured as the best of {1,2,4,8} against real end-to-end decode tok/s, not just the isolated microbench — see `gemv_q4_k.hip`'s module doc). `gemv_q6_k.hip` additionally replaced its per-`l` single-byte code loads with one 8-byte (`uint64_t`) load per lane per block (legal regardless of the 210-byte block's shifting 4-byte-alignment class since it goes through `memcpy`), fixing an ISA-confirmed ALU/instruction-count bottleneck (`global_load_d16_u8`/`_hi_u8` dominating) that Q4_K/Q5_K didn't have (LLVM already auto-vectorized their own per-byte loops into `global_load_b128`s). Net effect on Ornith-1.0-9B decode @ depth 2048: Q4_K_M 33.6->49.5 tok/s, Q6_K 18.1->41.8 tok/s; no prefill regression (the WMMA chunked-prefill path above is untouched). Any host site launching a `gemv_q*` kernel directly (not through `Kernels::gemv_quant`) must match this contract: `grid.x = m.div_ceil(ROWS_PER_WG)`, `shared_mem_bytes = REDUCE_BLOCK * ROWS_PER_WG * sizeof(f32)`.
  - `src/sample.rs`: host-side temperature/top-k/top-p sampling plus an optional off-by-default repeat penalty, driven by a deterministic inline xorshift64* PRNG (no `rand` dependency). `generate::generate` stays greedy-only (existing parity fixtures depend on exact argmax behavior); `generate::generate_sampled` takes a `SamplingParams`; `generate::generate_sampled_with_stop` additionally lets `on_text` request early termination, which is how `rocml-serve` enforces OpenAI `stop` strings against the growing decoded text.
- `rocml-cli` — `chat` (interactive REPL over `rocml::chat`, streamed via `StreamScanner`), `bench` (synthetic prompt/decode throughput harness, the llama.cpp-comparison baseline — `--turns N` switches it to issue #1's multi-turn snapshot benchmark, see `cmd_bench_turns.rs` and "Conversation-state snapshots" below), `generate` (one-shot completion; replaces the old `rocml/examples/generate.rs` smoke test, now rendering through the real chat template and sampler instead of a hardcoded format string), `models` (lists `rocml::registry::REGISTRY` with on-disk presence), `eval` (issue #15's agentic quality-eval harness — see "Agentic eval" below). `--model` on `chat`/`bench`/`generate`/`eval` accepts a registry name or a path — see `rocml::registry` below and `../README.md`'s "Model registry" section for the name table and override precedence. `chat` and `bench --turns` both take `--snapshot-ram-mb`/`--snapshot-dir`/`--snapshot-disk-mb` (`common::SnapshotArgs`).
- `rocml-serve` — OpenAI-compatible HTTP server (`POST /v1/chat/completions`, `GET /v1/models`). `src/worker.rs` is the one place that owns the loaded `Model`: a dedicated OS thread (HIP state isn't treated as `Send` in this codebase), fed by a `std::sync::mpsc` job queue and streaming results back per-job over a `tokio::sync::mpsc` channel — strictly sequential, no batching (the documented v1 concurrency model); it also owns the conversation-state `SnapshotStore` (issue #1, `--snapshot-ram-mb`/`--snapshot-dir`/`--snapshot-disk-mb`) and drives every job through `rocml::snapshot::turn::run_turn` rather than calling `rocml::generate` directly, logging a `tracing::info!` "snapshot hit"/"snapshot miss" per request. `src/mapping.rs` translates OpenAI wire shapes (`src/openai.rs`) to/from `rocml::chat` types (`map_sampling` merges a request's explicit fields onto `AppState::default_sampling`, sourced from the resolved model's registry preset); `src/routes.rs` builds the non-streaming full-JSON response, `src/sse.rs` the SSE one (split out purely for the 400-line cap — both drive off the same worker event stream via `routes::handle_request`). The chat renderer is hardcoded to Ornith-1.0-9B's template and used for every model it serves — see `../README.md`'s `rocml-serve` section for the one behavioral difference this causes (the `enable_thinking` default) and how a registry `--model` name now applies that model's own default automatically (`--no-think` still available, and always wins, for a path-based `--model` or to force it off). `RenderOpts { keep_history_reasoning: false, .. }` is always passed here (issue #9): a history assistant turn's `reasoning_content`/embedded `<think>` block is stripped by default, matching the Qwen3-family training convention rather than the raw template's own (verbatim-keeps-it) behavior — see `../README.md`'s "Think-block history" note and `rocml/src/chat/render.rs`. `src/debug.rs` is the optional `GET /debug/last_prompt` endpoint (`--debug-endpoints`, off by default): `routes::handle_request` records the exact rendered prompt into `AppState::debug`'s `LastPromptState` at request-accept time; `rocml_serve::build` only mounts the route when the flag is set.
- `rocml::registry` (`rocml/src/registry.rs`) — the compiled-in model catalog: `ModelSpec { name, family, gguf_rel, hf_repo, hf_file, default_ctx, sampling, thinking_default }` per known checkpoint, and `resolve(name_or_path, download)` turning a `--model` argument into a path, downloading via the `hf` CLI on a registry hit whose file is missing under the checkpoint dir. Every entry's `hf_repo`/`hf_file` is verified against the live Hugging Face API, not guessed — see the module's doc comments for each entry's verification note (e.g. `qwen3.5-2b`/`qwen3.5-0.8b` have no official Qwen-org GGUF, so they point at `unsloth`'s conversion instead; `ornith-9b` points at `ornith-ai`, the renamed `deepreinforce-ai`). `clamp_ctx` caps a requested context budget at this checkpoint's estimated VRAM budget (`crate::budget`, issue #3) with a warning naming the breakdown, rather than a hardcoded constant — see the "Long context / KV cache" section below.

## Build commands

Always use the Makefile, never ad-hoc `cargo` invocations:

- `make build` / `make test` / `make test-unit` / `make test-integration` / `make test-model`
- `make lint` (clippy `-D warnings` + `fmt --check`) / `make fmt`
- `make clean`
- `make serve` / `make bench` — run `rocml-serve` / `rocml-cli bench` against `QWEN_MODEL` (override with `QWEN_MODEL=/path/to.gguf make serve`)

**Always `CARGO_BUILD_JOBS=4`** — the Makefile exports it for every target already; if you run cargo directly for a one-off, set it yourself.

Real-GGUF tests and `make serve`/`make bench` resolve model checkpoints via `rocml_core::testpaths` (`rocml-core/src/testpaths.rs`): `$ROCML_CHECKPOINT_DIR` if set, else `$HOME/checkpoints` — expected to contain `Qwen3-0.6B-GGUF/Qwen3-0.6B-Q8_0.gguf`, `Qwen3.5-2B-GGUF/Qwen3.5-2B-Q8_0.gguf`, `Ornith-1.0-9B-GGUF/ornith-1.0-9b-Q6_K.gguf`, `Qwen3.5-2B-tokenizer/tokenizer.json`, and `Ornith-1.0-9B/chat_template.jinja`. Each test skips itself (with a message naming the resolved path) if its checkpoint isn't present. `rocml-core/tests/tokenizer_cross_validation.rs` additionally resolves a couple of files from the standard Hugging Face hub cache (`$HF_HOME/hub` else `$HOME/.cache/huggingface/hub`) via the same module's `hf_hub_file`.

`rocml::registry` (used by the CLI/server binaries, not by the tests above) resolves the same checkpoint dir independently — see that module's doc comment on why it mirrors rather than calls `testpaths::checkpoint_dir` — and can additionally populate it: a registry `--model` name whose file is missing there is downloaded via `hf download <repo> <file> --local-dir <dir>` unless `--no-download` is passed.

Tests in `rocml-hip`, the `rocml-kernels` integration tests, `rocml`'s forward pass, and `rocml-serve`'s end-to-end test require a real ROCm GPU (device init, actual kernel launches) — they are not mocked. Run on the machine with the GPU attached.

`make test-model` runs real-GGUF `--release` integration tests, each skipping itself if its checkpoint is absent (`make test` excludes all of them from the plain `cargo test --workspace` pass — they'd still build in debug, just run unbearably slowly — and runs them separately here):
- `greedy_parity`: dense Qwen3-0.6B (`<checkpoint dir>/Qwen3-0.6B-GGUF/Qwen3-0.6B-Q8_0.gguf`) greedy-decoded and checked against candle's independent CPU f32 implementation token-for-token.
- `qwen35_cpu_reference`: the qwen3.5 hybrid architecture's from-scratch pure-Rust f32 CPU reference (`tests/support/qwen35_cpu/`, no GPU) checked against Crane's fixture for a handful of tokens — isolates "did we understand the architecture" from "is the GPU kernel right".
- `qwen35_greedy_parity`: Qwen3.5-2B (`<checkpoint dir>/Qwen3.5-2B-GGUF/Qwen3.5-2B-Q8_0.gguf`) greedy-decoded on the GPU hybrid forward pass and checked against Crane's independent candle GPU implementation token-for-token, from fixtures in `rocml/tests/data/qwen35_greedy_fixtures.json`.
- `ornith_e2e`: Ornith-1.0-9B (`<checkpoint dir>/Ornith-1.0-9B-GGUF/ornith-1.0-9b-Q6_K.gguf`, qwen35 arch, Q6_K) — no independent reference for this checkpoint, so this asserts internal well-formedness instead: finite logits throughout a 24-token greedy decode, and the exact same generated token sequence from two independent model loads. Exists because this checkpoint only fits in 16GB VRAM through the quantized-weight path (see `LinearWeight` above).
- `rocml-serve`'s `server_e2e`: spawns the real router on an ephemeral port (Qwen3.5-2B) and drives it with a hand-rolled minimal HTTP/1.1 client (`tests/support/`) — non-streamed completion, streamed SSE, and a tools request. `two_turn_conversation_matches_output_with_snapshots_disabled` is issue #1's server-level gate: the same two-turn conversation against a server with the snapshot layer on vs. fully off (`--snapshot-ram-mb 0`) must produce byte-identical turn-2 output — it can't observe hit/miss through the HTTP API alone (`usage.prompt_tokens` reflects the tokenizer's full count regardless of reuse), so that half of the claim is instead asserted directly against `SnapshotStore`/`run_turn` in `rocml/tests/snapshot_equivalence.rs`. A companion `#[ignore]`d test in the same file (`ornith_tool_call_is_emitted`) asserts a real tool call against the Ornith GGUF; `make test-model` runs it as its own separate `cargo test` invocation (`cargo test --release -p rocml-serve --test server_e2e -- --ignored ornith_tool_call_is_emitted`) rather than alongside the default test, since the two would compete for VRAM. Both use a `JoinHandle`-based shutdown sequence (see `worker::spawn`'s doc comment) — skipping it crashes the test process on exit with "pure virtual method called" from a still-live worker thread racing the HIP driver's own teardown.
- `qwen35_chunked_prefill_parity`: issue #6's central correctness gate — on Qwen3.5-2B, `Model::forward_prompt`'s batched-chunk forward pass must produce the same result as the original token-serial one (`Model::forward_token`, called directly in this test's own reference loop) across prompt lengths `{1,4,127,128,129,500,2048}` (spanning every `CHUNK_CAP`/`PREFILL_CHUNK_SIZE` boundary). Asserts near-equal final logits (relative tolerance — reduction order differs between the two paths) and identical greedy continuations, with an explicit documented-near-tie escape hatch (large top-1/top-2 gap on a flip fails the test as a real bug; a tiny gap is logged, not failed). The final-logits tolerance was recalibrated from `1e-3` to `1e-2` when the WMMA follow-up landed (commit a9bdf53): `rows >= 128` chunks now go through f16-matrix-core rounding (measured max relative logit deviation 0.16%-0.55%), so the logits check is an order-of-magnitude guard while the exact-greedy half (near-tie escape) plus the issue-15 agentic eval remain the behavioral gates. Passes.
- `snapshot_equivalence`: issue #1's central correctness gate, one `#[test]` running four scenarios in sequence (deliberately not four separate tests — `cargo test`'s default parallelism loading up to 6 concurrent `Model`s would exhaust the dev GPU's 16GB) on Qwen3.5-2B: fp16-KV split-prefill-vs-restore equivalence across several boundaries including one straddling the 4096-token auto-snapshot interval; the same for the mixed Q8 KV cache; double-restore determinism (immutability); and a real `SnapshotStore`/`snapshot::turn::run_turn` two-turn hit. See "Conversation-state snapshots" above for why the logits bound is near-exact, not bitwise. Its final-logits tolerance was recalibrated from `1e-6` to `1e-2` when the WMMA follow-up landed (commit a9bdf53) — a restored-suffix prefill re-chunks at a different offset, mixing the f16 WMMA and f32 scalar paths — with exact greedy continuation still asserted. Passes.

`rocml/src/weights/linear.rs` also carries its own `#[cfg(test)]` per-layer spot checks (`cargo test --lib`, real hardware + real checkpoints, skip-if-missing): `LinearWeight::load` + `matvec` against one dense-Qwen3 tensor and one qwen3.5 GDN-layer/full-attention-layer tensor each, compared to `rocml-core`'s CPU dequant + a CPU dot product — this is the loader/dispatch layer, complementing the fused kernels' own tests in `rocml-kernels/tests/gemv_q*.rs`.

## Observability (issue #5)

`rocml/src/profile/` is a run-scoped `Profiler` that records per-op spans (layer index, op-kind — embed/norm/qkv/attn-decode/attn-out/gdn-conv/gdn-recur/gdn-out/ffn-gate-up/ffn-down/lm-head/layer — phase, bytes, FLOPs, wall time via `rocml-hip`'s `Event`/`elapsed_ms`), aggregated by `rocml/src/profile/report.rs` into per-layer and per-op-kind roofline rows (GB/s, GFLOP/s, % of the gfx1101 roofline — 624 GB/s / 17.5 TFLOP/s fp16 midpoint — plus a top-bottlenecks summary). `rocml/src/profile/cost.rs` holds the pure, unit-tested byte/FLOP formulas (analytical, not measured — `LinearWeight::byte_size()` supplies exact on-device weight sizes). `attn-decode` covers the fused decode-attention kernel (KV-cache append + flash-decoding online-softmax scores/weighted-V, see below); `attn-out` is just the output projection + residual add.

Threaded through both forward passes (`rocml/src/forward/`, `rocml/src/qwen35/forward/`) as `Option<&Profiler>` — a `Copy` type (the profiler uses `RefCell`/`Cell` internally), so it passes into every nested call by value with no `&mut` reborrow plumbing. Every instrumented call site is `Profiler::scope(prof, layer, op, bytes, flops, || { ...kernel calls... })`, which is a plain function call when `prof` is `None` — profiling off costs nothing. Decode gets full per-op granularity; the dense Qwen3 path's still-token-serial prefill loop times each layer as one `OpKind::Layer` span instead (bytes/flops still analytically broken out) to keep event count bounded at long `--depth` — see the module doc comment for the exact reasoning and the `MAX_TIMED_EVENTS` safety net. The qwen35 hybrid path's chunked prefill (below) gets the same full per-op granularity as decode, one event set per chunk (not per token) — event count stays bounded by construction since a chunk covers up to `PREFILL_CHUNK_SIZE` tokens per event set, not one.

`rocml-cli bench --profile` (report on the final of `--runs`, `--json` embeds it under `"profile"`) and `generate --profile` print the report. `bench --depth N` pre-fills N synthetic tokens through the normal prefill path before measuring decode t/s — reuses the same prefill/decode phase split `generate_sampled_profiled` already threads through `Profiler::set_phase`, so no separate code path was needed.

## Chunked prefill (issue #6)

The qwen35 hybrid architecture's prompt phase runs through a batched forward pass instead of the dense architecture's still-token-serial one (`crate::model::Model::forward_prompt` dispatches per architecture; only the hybrid arm chunks — see its own doc comment for why the dense path is out of this issue's scope). `qwen35::forward::Model::forward_prompt_chunked` splits the prompt into `PREFILL_CHUNK_SIZE` (512 as of the WMMA-pipeline round below — originally 128, chosen by measurement among {128,256,512} on Qwen3.5-2B `bench --depth 2048` back when the GEMM path was still scalar-FMA) token chunks and runs each through `forward_chunk`, which processes every layer with batched kernels instead of one launch per token:

- **Linear layers**: `gemm_xwt_f16`/`gemm_xwt_q{8_0,4_k,5_k,6_k}` (`rocml-kernels/kernels/gemm_f16.hip`/`gemm_xwt_quant.hip`), `out[rows,m] = X[rows,n] * dequant(W)^T` — the batched sibling of `gemv_f16`/`gemv_q*`, wired through `LinearWeight::matmul`. The quantized scalar kernels stage one dequantized weight tile in LDS per outer iteration and share it across `TILE_ROWS` (64: 8 warps x `ROWS_PER_WARP`=8) output rows per workgroup instead of re-dequantizing per row (each warp register-blocks its 8 rows with a `d`-outer/row-inner FMA loop reusing each LDS-loaded weight element across all 8, and defers the `__shfl_xor` cross-lane reduction to run once per row after the whole k-reduction instead of once per k-chunk — see `gemm_xwt_quant.hip`'s module doc for the measured ~750->~1700-1800 GFLOP/s win).
  - **WMMA matrix-core follow-up**: `gemm_xwt_wmma_q{8_0,4_k,5_k,6_k}` (`rocml-kernels/kernels/gemm_xwt_quant_wmma.hip`) feeds gfx11's wave32 matrix unit (`__builtin_amdgcn_wmma_f32_16x16x16_f16_w32`, raw intrinsic — no rocWMMA headers needed/available) instead of scalar FMA, closing most of the remaining gap to the f32 FLOP roofline: ~1.7 TFLOP/s scalar -> ~7.4-10.5 TFLOP/s WMMA at issue #6's acceptance shapes (rows=128, n=4096, m in {4096,8192,12288}), ~3.2x end-to-end chunked-prefill tok/s on real models (ornith-9b: 106->344 tok/s at depth 2048). Tile sizes (`TILE_ROWS`=128 = `PREFILL_CHUNK_SIZE` exactly, `TILE_M`=64, `K_STAGE`=16 — WMMA's minimum, empirically the fastest since a bigger `K_STAGE`'s LDS footprint costs more occupancy than it saves in sync overhead) were swept with a standalone hipcc harness outside cargo; see the kernel source's module doc for the fragment-layout derivation (confirmed against AMD's `amd_matrix_instruction_calculator` tool and a minimal probe before wiring in) and full tuning notes. `QuantKernels::gemm` (`rocml/src/forward/kernels_quant.rs`) dispatches to it whenever `rows >= 128`, `m >= TILE_M` (64), and `m`/`n` are multiples of 16, falling back to the scalar kernel otherwise (every chunk but a prompt's short last one — **and**, since the prefill-cleanup round below, any narrow-output projection with `m < 64`). **Known numeric trade-off** (documented in `kernels_quant.rs`, not fixed by loosening any test): rounding both GEMM operands to f16 for the matrix-core multiply is the issue's accepted ~5e-4 relative per-layer error, but it compounds across the whole hybrid model measurably more than the pure-f32 pipeline this replaced — `qwen35_chunked_prefill_parity`'s and `snapshot_equivalence`'s final-logits tolerances were recalibrated to `1e-2` for it (commit a9bdf53; measured max relative logit error ~0.16%-0.55%), while every *greedy-token* gate (near-tie escape hatch) passes unmodified — argmax decisions survive the precision drop even though raw logits shift, and the issue-15 agentic eval re-run on the WMMA build was outcome-identical (19/20 both quants, PPL 1.0800/1.0807).
    - **Narrow-`m` dispatch fix (prefill-cleanup round)**: the WMMA condition originally only checked `rows >= TILE_ROWS` and `m`/`n` multiples of 16 — Ornith's GDN per-head alpha/beta gate projections (`m = num_v_heads = 32`, a real shape, not synthetic) satisfied that and dispatched to WMMA anyway, whose grid is `(m.div_ceil(TILE_M), rows.div_ceil(TILE_ROWS))`: at `m=32 < TILE_M(64)` that's a **single** `grid.x` column, so the entire launch runs as one workgroup on one CU while the other 59 sit idle, serializing every `K_STAGE` reduction step with none of WMMA's usual cross-tile latency hiding. Adding `m >= GEMM_WMMA_TILE_M` to the dispatch condition (no change to the WMMA kernel file itself — it stays untouched per this round's scope) routes these to the scalar kernel instead, whose grid (`m, rows.div_ceil(64)`) makes `m` itself a grid dimension — full occupancy despite lower per-FLOP throughput. Found by temporarily splitting the bundled `gdn-conv` profiler scope (below) into its constituent kernels once the conv1d fix alone didn't move end-to-end tok/s; measured on ornith-9b @ depth 2048, these two projections alone cost ~294ms of a ~4.6s prefill. This single one-line dispatch-condition change was worth more end-to-end tok/s (443->485 @ depth 2048) than either of this round's two dedicated kernel rewrites below.
    - **Per-wave-efficiency round (issue #6 second follow-up)**: `docs/prefill-gap-analysis.md` found the WMMA GEMM's remaining gap wasn't occupancy (71% measured, `rocprofv3 --pmc OccupancyPercent`) but per-wave math density — 11.58/10.41 TFLOP/s on ornith-9b's ffn-gate-up/ffn-down was 66%/59% of the *practical* scalar-FMA-ceiling roofline but only ~15% of gfx1101's *true* 75 TFLOP/s WMMA peak. Two levers, both in `gemm_xwt_quant_wmma.hip` (see its module doc and `tests/gemm_xwt_quant_wmma_perf.rs`'s for full sweep tables): (1) grew each warp's accumulator tile from 1x2 to 2x2 16x16 fragments (`WARPS_M=8,WARPS_N=2`->`WARPS_M=4,WARPS_N=4`, `TILE_M` 64->128, `WARPS_PER_BLOCK` held at 16) so every LDS fragment load is reused across more WMMA ops; (2) padded the LDS row stride past `K_STAGE` by 8 halves (`ROW_STRIDE`=24) to break a 4-way bank-conflict pattern in the fragment-load gather. Both swept with a standalone hipcc harness (not checked in) interleaving configs in one process — cross-process `cargo test` runs on this machine showed up to 2x GFLOP/s swings from ambient GPU clock state alone, making that comparison method unusable for this round. The old kernel's grid was `channels.div_ceil(256)` blocks (32 for Ornith's 8192-channel `conv_dim`) regardless of `chunk_len` — at most 32 of gfx1101's 60 CUs ever had a block scheduled. ## Long context / KV cache (issue #3, issue #2)

Context length is a load-time parameter, not a hardcoded cap: `rocml::LoadOptions { ctx, kv_cache }` is threaded through `Model::load` (both `forward::Model`/`qwen35::forward::Model`) and used to size `KvCache`/`HybridCache` directly — the old `crate::cache::MAX_SEQ_CAP` constant is gone. `rocml::KvCacheMode` is `Fp16` (default), `F32` (parity-test-only — see below), or `Q8`/`Q4Mixed` (issue #2, KIVI-style — implemented for the qwen35 hybrid architecture only; the dense `forward::Model::load` still rejects a quantized mode with a clear error). CLI (`chat`/`bench`/`generate`/`eval`) and `rocml-serve` expose `--ctx`/`--kv-cache`/`--mmq` (the last, `LoadOptions::use_mmq`, is the qwen35 chunked-prefill int8-MMQ dispatch flag from the "Chunked prefill" section above — default `false`, unrelated to KV cache dtype); `bench`'s own `--ctx` default is big enough for whatever `--depth`/`--decode-tokens` needs rather than falling back to a registry preset.

`crate::budget` (`rocml/src/budget.rs`) holds the VRAM math: `kv_bytes_per_token(n_cache_layers, n_kv_heads, head_dim, dtype)` (dense: every layer; hybrid: only full-attention layers — GDN state is O(1)) plus a fixed `ACTIVATION_HEADROOM_BYTES` (768 MiB, measured-generous) make up a `Budget`, which answers `max_ctx()`/`fits(ctx)`/`usage_fraction(ctx)`/`breakdown(ctx)`. Two integration points, deliberately different in precision: `registry::clamp_ctx` (`budget::estimate_from_gguf`) is a *pre-load* heuristic using the GGUF file's on-disk size as a generous proxy for on-device weight bytes (real bytes are only known once `LinearWeight::load` actually uploads them — the proxy never under-estimates for this registry's quant configs, since a raw-quant tensor uploads byte-identical to its file bytes and an f32-source tensor gets *halved* on upload); `Model::load` then performs the *authoritative* post-weights-load check with real `hipMemGetInfo` numbers, erroring (`RocmlError::VramBudget`, naming the breakdown and a suggested max ctx) if the estimate was too optimistic, and warning above 90% predicted usage either way.

KV cache storage dtype (issue #3's Stage A) is per-load, not per-tensor: `crate::cache::KvDtype::F16`/`F32`, chosen by `KvCacheMode::dense_dtype()`. Both `KvCache` (dense) and `qwen35::cache::AttnPlane` (hybrid) store K/V as an enum over `DeviceBuffer<half::f16>`/`DeviceBuffer<f32>`, exposing only a dtype-erased `k_ptr()`/`v_ptr()` (`DevPtr`) plus a `dtype()` discriminant — every call site (`forward::attention`, `qwen35::forward::attention`/`attention_chunk`) matches on `dtype()` to pick the matching kernel pair (`Kernels::attn_decode`/`attn_decode_f16`, `attn_prefill`/`attn_prefill_f16`, `ChunkKernels::scatter_kv_chunk`/`scatter_kv_chunk_f16`) rather than branching inside a single generic kernel launch. On the HIP side, `attn_decode.hip`/`attn_prefill.hip`'s `load_kv_f32` seam (see their own module docs) is now a C++ template, `load_kv<T>` with `float`/`__half` specializations, wrapping a templated `_impl` device function that both the `_f32` and `_f16` `extern "C"` entry points call — one source of truth for the online-softmax tiling logic, and the seam a future quantized-KV read (issue #2) slots into the same way. `KvF16Kernels` (`rocml/src/forward/kernels_kv.rs`) owns the f16-path kernel handles, split out of `kernels.rs` purely for the 400-line file cap (mirrors `kernels_quant.rs`'s `QuantKernels` for the same reason).

Parity tests (`greedy_parity`, `qwen35_greedy_parity`, `qwen35_chunked_prefill_parity`) explicitly request `LoadOptions::new(ctx).with_kv_cache(KvCacheMode::F32)` to pin the exact pre-issue-#3 reference numerics their fixtures were captured against; the default (`Fp16`) is covered separately by `kv_dtype_parity.rs`'s dedicated fp16-vs-f32 logits/greedy-decode comparison (near-tie escape hatch, same policy as the chunked-prefill suite — a large gap fails, a tiny one is logged).

### Quantized KV cache (issue #2, KIVI-style, phase 1)

`crate::kv_quant` (`rocml/src/kv_quant/`) is the pure, GPU-free foundation: `layout::MixedLayout` tracks one mixed layer's sink/bulk/window region boundaries (`SINK_LEN`=32, `WINDOW_LEN`=128, fixed constants, not yet CLI-tunable) and answers which region a position lives in plus whether appending it triggers a *whole-window* batch eviction (never per-position — matches issue #2's own review comment); `quant_math` is the CPU reference for K per-channel Q8 and V per-token Q8/Q4 (4-bit packed 2 codes/byte, low nibble = even channel), checked in both `rocml`'s own unit tests and `rocml-kernels/tests/kv_quant.rs`'s kernel-vs-reference tests.

`qwen35::cache_mixed::MixedAttnPlane` (now a small directory module, `cache_mixed/mod.rs` + `cache_mixed/chunk.rs`, split for the 400-line cap) owns one mixed layer's device buffers (sink/window f16, bulk K int8 codes + per-(head,block,channel) f32 scales, bulk V int8/packed-nibble codes + per-(head,position) f32 scales) and orchestrates `append`: sink write for `pos < SINK_LEN`, else append into the window, quantize-evicting the whole window in one batch first if it was already full. `qwen35::cache::HybridCache::new(cfg, ctx, mode)` applies the **boundary-layer skip**: the first and last full-attention layers (by position among full-attention layers specifically) always get a dense fp16 `AttnPlane` regardless of `mode`; only layers strictly between them become `AttnLayerCache::Mixed` when `mode.is_quantized()`. `qwen35::forward::attention::attention_step` dispatches on that enum, calling `MixedKernels::attn_decode_partial_mixed` (`kernels/attn_decode_mixed.hip`'s `attn_decode_partial_mixed_q8`/`_q4` — a per-position dequant-on-load inline in the same online-softmax tile loop `attn_decode_f16` uses, sharing the dtype-independent `Kernels::attn_decode_reduce`) for Mixed layers.

`budget::mixed_kv_bytes_per_token` accounts for the mixed layout precisely: boundary layers via the plain dense formula, mixed layers via a per-token bulk cost (K code + amortized per-block scale, V code + per-token scale) plus a fixed sink+window overhead independent of ctx (`Budget` gained a `fixed_overhead_bytes` field/`_with_overhead` constructor variants to carry it) — both `registry::clamp_ctx` and `Model::load` (qwen35) use it.

**Debugging note for future kernel work in this area**: `mixed_kv_parity.rs`'s first draft compared the *prompt's* logits between fp16 and quantized modes and measured an exact 0.0 difference — a false negative, not a passing result: `PROMPT_LEN` (32) equals `SINK_LEN` exactly, so the prompt alone never reaches the window/bulk regions where quantization applies. Always compare logits from a decode step well past `SINK_LEN + WINDOW_LEN` (160) when validating this cache.

#### Chunked mixed-KV prefill (issue #2's chunked-prefill follow-up)

The token-serial fallback described above is gone: `qwen35::forward::Model::forward_prompt` now always calls `forward_prompt_chunked` regardless of `KvCacheMode` — `HybridCache::has_mixed_layers()`/`attn_dense_mut` were removed as dead code once `chunk_forward.rs`'s per-layer dispatch could handle both `AttnLayerCache` variants (`attention_chunk::attention_chunk_step` for `Dense`, `attention_chunk_mixed::attention_chunk_step_mixed` for `Mixed`, matched via `HybridCache::attn_mut`'s enum return).

- **Chunked append (`cache_mixed/chunk.rs`, `MixedAttnPlane::append_chunk`)**: `crate::kv_quant::layout::MixedLayout::plan_chunk_append(pos_base, chunk_len)` (pure Rust, no GPU — `layout/chunk_plan.rs`, split out of `layout/mod.rs` for the 400-line cap) is the batched sibling of `prepare_append`: it returns how many leading rows land in the sink, plus a list of window `ChunkWindowSegment`s (`chunk_row_start`/`len`/`window_slot_start`/`evict_after`), each replaying *exactly* what `chunk_len` sequential `prepare_append` calls would compute — same physical window slots, same eviction trigger points (a block only evicts when the position that *would* overflow it is actually appended, never early), same `window_base` bookkeeping. `WINDOW_LEN` (128) equaled the production `PREFILL_CHUNK_SIZE` exactly at issue #2's original writing, so a chunk triggered at most one eviction in practice — the WMMA-pipeline round raised `PREFILL_CHUNK_SIZE` to 512 (4x `WINDOW_LEN`), so a single production chunk can now trigger up to 4 evictions; the algorithm always handled any `chunk_len` (multiple evictions per call) correctly regardless, and `mixed_kv_chunked_prefill_parity.rs`/`kv_dtype_parity.rs`/`mixed_kv_parity.rs` were re-run and still pass unmodified at the new chunk size — verified by `layout/chunk_plan.rs`'s own unit tests, including a 50-trial deterministic-xorshift fuzz test replaying random chunkings of the same token range against a token-serial `prepare_append` trace and asserting an exact match (window slots, eviction sequence, final `window_base`) every time.
  - **No new kernels were needed for the write path.** `quantize_evict_k`/`_v` (`kernels/kv_quant.hip`) already process a whole `WINDOW_LEN`-token block in one launch — that was the "batched" design issue #2 shipped with from the start — and `ChunkKernels::scatter_kv_chunk_f16` (already used by the dense chunked-prefill path for its own KV-cache append) already batches an arbitrary contiguous row range's fp32->fp16 cast-and-copy into a `[n_kv_heads, max_seq, head_dim]`-shaped destination, which is exactly the sink's and window's own physical layout at `max_seq = SINK_LEN`/`WINDOW_LEN` respectively. `append_chunk` just calls these two existing kernels the right number of times, at the right offsets, in the right order (write a segment, then — if it triggered an eviction — quantize-evict *before* the next segment overwrites the window). This is also why the resulting cache state's *placement* is bit-identical to token-serial: every element still goes through the identical kernel/arithmetic path, just batched into fewer, larger launches instead of `chunk_len` tiny ones.
- **Chunked read**: `kernels/attn_prefill_flash_mixed.hip` (new file) is the chunked-prefill sibling of `attn_decode_mixed.hip` — the same `BR`-row-tile x split-K design `attn_prefill_flash.hip` uses for the dense KV plane (see the flash-prefill section below), except each K/V element is read through `attn_common.h`'s shared `load_mixed_kv`/`load_bulk_v` templates instead of a flat buffer. Those templates were *factored out of* `attn_decode_mixed.hip` in this round (previously private to that file) specifically so the decode and chunked-prefill mixed-read paths share one dequant implementation and can't drift apart — `attn_decode_mixed.hip`'s own behavior is unchanged (verified: its existing kernel-vs-CPU-reference tests still pass byte-for-byte after the refactor). The reduce pass is *not* duplicated: `attn_prefill_flash_reduce_f32` (dtype/source-independent, only reads the f32 partial scratch buffers) is reused as-is. Host launcher: `qwen35::forward::kernels_flash_mixed::FlashPrefillMixedKernels` (new file, mirrors `kernels_mixed.rs`'s v_bits-dispatch pattern), reusing `crate::forward::kernels_flash`'s existing split-K sizing heuristic (`attn_prefill_flash_splits`) and scratch buffers (`ChunkScratch`'s `attn_flash_partial_{out,m,l}`/`attn_concat` — already sized generously enough, no new scratch allocated).
  - **Always flash, no depth threshold.** Unlike the dense path (`USE_FLASH_PREFILL_MIN_DEPTH`=512, below which `attn_prefill.hip`'s single-pass kernel wins on launch overhead), `attention_chunk_mixed.rs` dispatches to the flash-mixed kernel unconditionally. No shallow-depth mixed kernel exists: issue #2's mixed cache targets long-context (150K) workloads where depth is always well past that threshold in practice, and the flash kernel degrades gracefully to `n_splits==1` at shallow depth (one extra, cheap reduce launch — not a correctness concern, and every prompt length this issue's own parity suite and acceptance criteria care about is either past 512 already or short enough that the extra launch is noise).
- **New correctness gates**: `rocml/tests/mixed_kv_chunked_prefill_parity.rs` (model-level, both `q8`/`q4-mixed`, prompt lengths `{32, 128, 160, 500, 2048}` spanning the sink/ring boundaries) asserts every mixed layer's `window_base` matches chunked-vs-token-serial *exactly* (pure integer bookkeeping, no floating point involved, so this has no excuse to drift — and doesn't, in measurement) plus near-identical cache bytes and logits with the measured bound reported honestly (see the test's own module doc: cache-byte absolute diff measured up to `0.42` for Q4Mixed at one prompt length — a few outlier channels several evictions deep, where Q4's coarse quantization amplifies the same WMMA/GDN-chunkwise reduction-order drift `qwen35_chunked_prefill_parity.rs` already documents for the dense path — yet greedy continuation matched *exactly* with zero divergence across all 5 prompt lengths x 2 modes). `rocml-kernels/tests/attn_prefill_flash_mixed.rs` (kernel-level) checks the new flash-mixed kernels against an independent CPU causal-softmax reference across sink/bulk/window regions, multiple query rows, GQA groups, split-K, and both `V_BITS`.
- **Rejected approach**: a dedicated multi-token variant of the quantize-evict kernels was considered (per the issue brief's own suggestion) but turned out unnecessary once `quantize_evict_k`/`_v`'s existing one-launch-per-block design was re-examined — it already *is* the multi-token batched kernel the issue asked for; the only missing piece was the Rust-side orchestration (`plan_chunk_append`) to call it the right number of times per chunk instead of once per decode step.
- **Zero-length-segment bug found by `snapshot_equivalence.rs`**: a chunk whose `pos_base` lands exactly on a "window just became full, not yet evicted" boundary (`prepare_append`'s own semantics: eviction fires on the position that *would* overflow the window, not the one that fills it) produces a `ChunkWindowSegment` with `len == 0` whose `evict_after` still fires — the very first position of the new chunk is exactly the overflow-triggering one. This is unreachable from a fresh `forward_prompt` call starting at position 0 (chunk boundaries are multiples of `PREFILL_CHUNK_SIZE` — 128 at issue #2's writing, 512 as of the WMMA-pipeline round, either way still a multiple of `WINDOW_LEN`=128 — while eviction boundaries are at `SINK_LEN + 128*k`, a different residue mod 128, so they never coincide), which is why `mixed_kv_chunked_prefill_parity.rs` didn't catch it; it's exactly what a snapshot restore at a non-chunk-aligned position (e.g. `SINK_LEN + WINDOW_LEN` = 160) produces, which is what `snapshot_equivalence.rs`'s pre-existing mixed-cache scenario did. A zero-row `scatter_kv_chunk_f16` launch has a zero grid dimension, which HIP rejects with "invalid argument" — `MixedAttnPlane::append_chunk` must skip the scatter call for a zero-length segment while still running its eviction. Locked in by a dedicated `layout/chunk_plan.rs` unit test asserting the exact zero-length-segment shape.
- **Measured** (ornith-9b, Q4_K_M, `bench --depth {2048,8192,16384}`, median of 3 runs): prefill tok/s —

  | depth | fp16 | q8 | q4-mixed |
  |---|---|---|---|
  | 2048 | 495.2 | 492.8 (-0.5%) | 491.3 (-0.8%) |
  | 8192 | 426.3 | 421.1 (-1.2%) | 416.7 (-2.3%) |
  | 16384 | 359.2 | 352.3 (-1.9%) | 348.0 (-3.1%) |

  Both quantized modes land within ~3% of fp16 at every depth tested — far inside the ≤25%-at-depth-2048 acceptance bound, and the gap barely widens with depth despite the mixed cache's extra per-chunk overhead (the append-side quantize-evict launches; the read-side dequant-fused load doing more per-element ALU work than a flat f16 load). **Does not beat fp16 at depth 16384** — the "faster if the bandwidth math holds" hypothesis this round's brief posed didn't materialize: prefill attention is only ~30-40% of total prefill time even at depth 16384 (per the flash-prefill round's own measurement above), so a bandwidth win confined to that op's K/V reads is diluted by the ~60-70% of prefill time (GEMMs, GDN chunkwise recurrence) the mixed cache doesn't touch at all, while the mixed path's own added overhead (extra kernel launches, heavier per-element dequant) is a real, if small, tax. Net: this round is a capacity/decode-bandwidth win (issue #2's original point) that now *also* keeps chunked-prefill throughput intact at long context, not a prefill speedup in its own right. Decode confirmed flat throughout (e.g. ornith-9b: 49.4/48.7/49.0 tok/s @ 2048, 45.8/45.0/45.1 @ 8192, 40.7/39.3/39.5 @ 16384 across fp16/q8/q4-mixed respectively — within run-to-run noise); the fp16 chunked-prefill path itself is untouched (no changes to `attn_prefill_flash.hip`/`kernels_flash.rs`/the dense `attention_chunk.rs` dispatch).

## Conversation-state snapshots (issue #1)

`rocml/src/snapshot/` is an immutable checkpoint store for the qwen35 hybrid architecture's full decode state (GDN recurrence + linear full-attention KV) at a token position, addressed by an exact token-id prefix match — the point being that agentic workloads re-send a growing conversation every turn, and GDN state is O(1) in position, so restoring a snapshot and prefilling only the new suffix turns per-turn prefill from O(conversation) into O(new tokens). **Dense `qwen3` is out of scope**: its KV cache is O(position) per layer with no fixed-size state, and it has no chunked prefill to hook capture into; `crate::model::Model::as_hybrid`/`as_hybrid_mut` is how every integration point (below) detects the architecture and skips snapshot logic entirely for `Dense`.

- **Identity/hashing** (`snapshot::hash`): a hand-rolled FNV-1a `ChainHash` folded one token at a time — "chain"/"rolling" because a longer prefix's hash resumes from a shorter prefix's already-computed value instead of rehashing from token 0. It's a fast bucketing pre-filter only; the actual "exact match" guarantee comes from comparing `SnapshotData::token_ids` (stored in full — 4 bytes/token, negligible) byte-for-byte before ever accepting a candidate (`ram::RamStore::find_best`/`disk::DiskStore::find_best`).
- **Content** (`snapshot::types`): `SnapshotData { position, token_ids, gdn: Vec<Option<GdnLayerBytes>>, attn: Vec<Option<AttnLayerBytes>> }`, indexed by layer. `GdnLayerBytes` is always captured whole (O(1) in position). `AttnLayerBytes::DenseF16`/`DenseF32` capture only the *filled* `[0, N)` prefix of each kv head's plane, never the whole allocated `max_seq` capacity — new `DeviceBuffer::copy_range_to_host`/`copy_range_from_host` (`rocml-hip/src/buffer.rs`) exist for exactly this. `AttnLayerBytes::Mixed` (issue #2's KIVI cache) captures sink/window whole (fixed-size) but — a deliberate v1 simplification — captures the **whole allocated bulk region**, not just the evicted-so-far prefix: `bulk_k_codes`/`bulk_v_codes`'s per-head/per-block physical layout inside the larger buffer is an internal contract of `quantize_evict_k`/`_v`'s HIP kernels that isn't exposed for reuse here, so slicing precisely would risk a silent mismatch; correctness is unaffected (unfilled blocks are never read), only snapshot size for mixed layers scales with configured `ctx` rather than actual position. Capture/restore live as methods on the owning types themselves (`qwen35::cache::{GdnLayerState,AttnPlane,AttnLayerCache,HybridCache}` in a child `cache::snapshot` module, `qwen35::cache_mixed::MixedAttnPlane`, `qwen35::forward::Model` in `forward/snapshot.rs`) — every capture/restore is a plain D2H/H2D memcpy, never a re-quantization.
- **Identity/config gating**: `ModelStamp { gguf_path, file_len }` (cheap, not a full-file hash) and `KvConfigStamp { mode, ctx }` — `ctx` matters because `AttnPlane`/`MixedAttnPlane` buffer offsets (and `bulk_cap`) are sized from it, so a snapshot captured at one `ctx` is a documented miss (never a reshape attempt) at another.
- **Tiers** (`snapshot::{ram,disk}`, combined by `SnapshotStore`): host-RAM LRU (`RamStore`, `--snapshot-ram-mb`, default 4096, `0` disables) always constructed; optional NVMe (`DiskStore`, `--snapshot-dir`, off by default, `--snapshot-disk-mb`) content-addressed files (`{model_kv_id}-{chain_hash}-{position}.snap`, a magic+FNV-1a-checksum framed payload) plus a JSON index for size-budgeted LRU eviction. Corruption at any layer (truncated/bit-flipped `.snap` file, malformed `index.json`) degrades to a deleted file + miss / an empty fresh index — never a crash, never propagated as an error. `SnapshotStore::lookup` never returns a full-length match (always leaves at least one token to prefill) and promotes a longer disk hit into RAM on read.
- **Capture points**: after prompt prefill completes, after each completed generation (end-of-turn), and every 4096 *absolute* tokens during a long prefill — all three fall out of one mechanism in `generate::resumed::generate_core` (`rocml/src/generate/resumed.rs`): the prefill loop splits an outer `forward_prompt` call into `PREFILL_CAPTURE_INTERVAL`-token segments and fires a `prefill_boundary` callback after each (so a short prompt's single segment covers "after prefill", and a long one also fires mid-prefill), plus one more explicit capture after decode. **This makes the resumed logits only near-exact, not bitwise-equal**, to a monolithic full-prefill run: the hybrid path's chunked kernels re-chunk each call's own slice from its own index 0, so a split off a 128-token boundary changes which tokens share a batched GEMM/attention/GDN-chunk launch — the same reduction-order sensitivity `qwen35_chunked_prefill_parity.rs` documents for chunked-vs-serial. `rocml/tests/snapshot_equivalence.rs` is the dedicated gate (relative-tolerance logits + exact-or-documented-near-tie greedy continuations), covering fp16, the mixed Q8 cache, a split straddling the 4096 boundary, immutability (double restore), and a real `SnapshotStore`/`run_turn` hit.
- **Orchestration** (`snapshot::turn::run_turn`): the one function `rocml-serve`'s worker, `rocml-cli chat`, and `rocml-cli bench --turns` all drive — reset, lookup + restore on a hit, resumed prefill (with the periodic capture above), sampled decode (OpenAI `stop` strings optional, pass `&[]` for the CLI REPL), then an end-of-turn capture. Deliberately outside `generate`'s hot loop: lookup/capture only happen at turn/segment boundaries, never per decode token. Returns `reused_prefix`/`restore_seconds`/`capture_seconds` for logging (`rocml-serve` via `tracing::info!("snapshot hit"/"snapshot miss")`; `rocml-cli chat` via `eprintln!`).
- **CLI/server flags**: `--snapshot-ram-mb` (default 4096), `--snapshot-dir` (default off), `--snapshot-disk-mb` (default 20000) on `rocml-serve` and on `rocml-cli chat`/`bench` (`common::SnapshotArgs`, flattened). `rocml-cli bench --turns N` (`cmd_bench_turns.rs`) simulates a growing conversation (`--turn-decode-tokens`, default 300, generated per turn on top of a fixed synthetic user message) and reports per-turn prefill latency/reuse/restore/capture timing; `--no-snapshots` disables the layer for a baseline run (no automatic on/off comparison in one invocation — run the command twice, matching every other `bench` flag's style).
- **A latent bug this uncovered and fixed**: `HybridCache::reset()` zeroed GDN state but never rewound a mixed-KV-cache layer's `MixedAttnPlane`'s eviction bookkeeping (`window_base`) — harmless for a dense `AttnPlane` (stale bytes past the new sequence's position are simply never read) but not for `window_base`, which is position-*independent* persistent state. A second sequence on the same loaded model (i.e. `rocml-serve` handling a second request) under `--kv-cache q8`/`q4-mixed` would leave `window_base` stale, and in a release build (where the guarding `debug_assert!` compiles out) the next `pos - window_base` computation underflows into a huge offset that panics deep in a kernel launch. Fixed by having `HybridCache::reset()` also call `MixedAttnPlane::reset()` (just `self.layout = MixedLayout::new()`, no device buffer needs zeroing). Found by `snapshot_equivalence.rs`, which is the first test in this codebase to reset-and-reprocess a mixed-cache model more than once — independent of the snapshot layer itself.

## MTP speculative decoding (issue #8) — investigated, not implemented

Issue #8 asked whether Ornith-1.0-9B's checkpoint ships the 1-layer MTP (multi-token-prediction) head llama.cpp/HF-transformers use for speculative decoding on Qwen3.5-hybrid/DeepSeek-family models, and if so to wire up draft-and-verify decode. **Result: the flagship registry checkpoint has no MTP weights in any form this repo can load — GGUF or safetensors — so Phase 2 (draft-and-verify decode) was not started.** This is a documented negative, not an oversight: verified two independent ways below, both decisive.

- **GGUF (both registry entries)**: `rocml-core/examples/inspect_gguf.rs` (new, throwaway tensor-listing tool — `cargo run -p rocml-core --example inspect_gguf -- <path.gguf>`, dumps tensor count, max `blk.N` index, every tensor for the last block +1, and greps for `mtp`/`nextn`/`eh_proj`/`enorm`/`hnorm` anywhere in the tensor name table) run against both `Ornith-1.0-9B-GGUF/ornith-1.0-9b-Q4_K_M.gguf` and `.../ornith-1.0-9b-Q6_K.gguf`: `qwen35.block_count: 32`, 427 tensors, max `blk.` index **31** (i.e. `blk.0`..`blk.31` only — no `blk.32`), zero matches for any MTP-suspicious substring. Both quants are consistent with each other and with `config.json`'s `num_hidden_layers: 32`.
- **HF safetensors (`/mnt/nvme/miksa/checkpoints/Ornith-1.0-9B`)**: the issue's own framing assumed this checkpoint "definitely has the full MTP weights" — it does not. `model.safetensors.index.json` (760 tensors total, `model.language_model.layers.0`..`31`, plus a full `model.visual.*` vision tower — this checkpoint is VL-capable) has zero tensors matching `mtp`/`nextn`/`eh_proj` under any prefix, despite `config.json`'s `text_config.mtp_num_hidden_layers: 1` / `mtp_use_dedicated_embeddings: false` declaring the *architecture* supports an MTP head. Cross-checked against the live HF repo listing (`api/models/ornith-ai/Ornith-1.0-9B`) to rule out a locally-incomplete download: the remote file list matches the local checkout exactly, and the sibling `ornith-ai/Ornith-1.0-35B` (a different size in the same 1.0 line) also ships zero MTP tensors — the entire Ornith-1.0 generation appears to have shipped without the MTP head, config metadata notwithstanding.
- **Where the MTP head does exist**: `ornith-ai/Ornith-1.5-9B` (a newer, larger checkpoint — not the flagship this repo's registry uses) *does* ship one, confirmed via a range-GET of its final shard's safetensors header (no full download needed): `mtp.pre_fc_norm_hidden.weight [4096]` (hnorm — RMSNorm on the previous layer's hidden state), `mtp.pre_fc_norm_embedding.weight [4096]` (enorm — RMSNorm on the new token's embedding), `mtp.fc.weight [4096, 8192]` (eh_proj: linear on `concat(hnorm_out, enorm_out)` → `[4096]`), `mtp.layers.0.*` — **one standard full-attention transformer layer** (`self_attn.{q,k,v,o}_proj` shapes `[8192,4096]`/`[1024,4096]`/`[1024,4096]`/`[4096,4096]`, `q_norm`/`k_norm [256]`, `input_layernorm`/`post_attention_layernorm [4096]`, SwiGLU MLP `gate_proj`/`up_proj [12288,4096]`/`down_proj [4096,12288]`) — bit-for-bit the same shapes as this model's own full-attention layers, **not a GDN layer** — then `mtp.norm.weight [4096]` before the shared embedding/lm_head. Textbook DeepSeek-V3-style MTP module. This is recorded here purely for the next person's benefit if a future issue adds `ornith-1.5-9b` to the registry — the design in that case would be exactly what issue #8 specified (chain the head, verify via the existing chunked-prefill path, snapshot GDN state around the verify pass), just with a real weight source. **Not implemented against Ornith-1.0-9B**: bolting a different checkpoint's MTP head onto this model's hidden-state space would not be speculative decoding in any meaningful sense (the head is trained jointly with its own backbone's representations) — the issue's own "don't force a win" clause applies squarely here, so this was not attempted.
- **Disposition**: no Phase 2 code, no new CLI/LoadOptions flags, no bench numbers (there is no draft source to measure) — the existing decode path is untouched. `rocml-core/examples/inspect_gguf.rs` is kept as a small reusable dev tool for the next model/tensor-presence question, not wired into any Makefile target (it's a one-off inspection aid, not a shipped feature).

## Agentic eval (issue #15)

`rocml-cli eval` (`cmd_eval.rs` + `rocml-cli/src/eval/`) measures quantization loss on real tool-use tasks — greedy/deterministic scenarios through the actual chat protocol, in-process, not through `rocml-serve` — rather than wikitext PPL, the harness that decided Q4_K_M is the default `ornith-9b` registry entry (Q6_K remains as `ornith-9b-q6`). Split into small files purely for the 400-line cap; `cmd_eval.rs` owns CLI parsing and the top-level run/resume loop, `eval/` holds the pieces:

- `eval::scenario` — the JSON schema (`bench/eval/scenarios.json`, checked in, 20 hand-authored scenarios) for the four scenario kinds: `tool_choice` (exactly one expected tool call + arguments), `no_tool` (zero tool calls), `multi_turn` (an expected first tool call, a canned tool result fed back, then either a second expected tool call or a final-answer substring), `long_context` (a retrieval needle in ~4000/~8000 tokens of filler).
- `eval::filler` — deterministically generates `long_context` filler prose from a `u64` seed and a small fixed wordlist (a local xorshift64* PRNG, not `rocml::sample::Rng` — that struct's RNG internals are private to the `sample` module) so scenarios store only the needle, its position fraction, and a target length, never kilobytes of filler text.
- `eval::runner` — drives one scenario: renders messages via `rocml::chat::render` (thinking on, matching Ornith's own default), decodes via `snapshot::turn::run_turn` with `store: None` (which reduces that function to "reset, full prefill, greedy decode" — every turn is scored as a fully independent, deterministic reprocess, no snapshot reuse in the loop), parses the reply with `rocml::chat::parse_assistant_output`.
- `eval::scorer` — pure pass/fail rules against a parsed `AssistantOutput`, unit-tested with canned outputs (no GPU). Tool-call argument matching accounts for the parser's own contract: every scalar argument comes back as a `Value::String` regardless of logical type (see `chat::parser::parse_argument_value`'s doc comment), so expected numbers are compared numerically (parsed from that string) and expected strings after trimming whitespace, never by raw `Value` equality.
- `eval::ppl` — the secondary signal: teacher-forced perplexity over `bench/eval/corpus.txt` (a small public-domain excerpt), one forward pass per token via `Model::forward_token` (not `forward_prompt`, which only returns the last position's logits) — cheap enough at ~2-3K tokens that a batched shortcut isn't worth the complexity.
- `eval::results` — the results JSON shape (`{label, timestamp_unix, git_rev, model_path, engine_config, per_scenario[], aggregates{}, ppl}`) plus incremental save: `--out` is rewritten after every scenario (and again after PPL), so a run killed partway through a 30-60 minute eval can resume with `--resume`, which skips any scenario id already present in that file.

`make eval` runs both `ornith-9b-q6` and `ornith-9b` at ctx 16384 (long-context scenarios need ~8K tokens of filler plus thinking/answer headroom), `--resume` always on, writing `bench/eval/results/{ornith-q6k-fp16kv,ornith-q4km-fp16kv}.json`.

## Kernel build pipeline

`rocml-kernels/build.rs` shells out to `hipcc` for every `*.hip` file under `kernels/`:

```
${ROCM_PATH:-/opt/rocm}/bin/hipcc --genco --offload-arch=${ROCML_GFX_ARCH:-gfx1101} -O3 -o $OUT_DIR/<name>.hsaco <src>
```

The resulting `.hsaco` code objects land in `$OUT_DIR` and are pulled into the crate via `include_bytes!`, so the compiled binary carries the kernels — no runtime dependency on `hipcc` or the `kernels/` sources being present. `rocml-hip::module::Module::load_from_bytes` takes those bytes straight to `hipModuleLoadData`.

- Override the target GPU architecture with `ROCML_GFX_ARCH` (default `gfx1101`). Building for a different card (e.g. gfx1030, gfx90a) is just re-running the build with that env var set — no source changes needed unless the kernel itself is arch-specific.
- Override the ROCm install root with `ROCM_PATH` (default `/opt/rocm`) — used both to find `hipcc` and to locate `libamdhip64.so` for linking (`rocml-hip/build.rs`).
- `build.rs` reruns on changes to `kernels/` and to `ROCM_PATH`/`ROCML_GFX_ARCH`; a `hipcc` failure fails the build with its full stderr.
